# CLAUDE.md — инструкция для следующего агента

## Что это

RL-среда для Genesis Hackathon (FinTech, онлайн-отбор). Задача организаторов — **среда**
для дообучения ИИ-аудитора, а не агент, UI или чат-бот. Жюри запускает свои 4 политики
(random, simple reconciliation, flag-all, oracle) на 20 скрытых эпизодах и ставит баллы
за корректность среды и оценщика:

| Критерий | Баллы |
|---|---|
| Контракт и изоляция | 25 |
| Данные и эталон | 25 |
| Надёжность награды | 25 |
| Воспроизводимость и обобщение | 15 |
| Инженерия и объяснение | 10 |

**Дедлайн сдачи: 22 ноября 2026, 23:59 по Астане.** Утечка эталона, запись в оценщик
или неработающее ядро блокируют оценивание. За UI и обучение модели баллов нет.

## Команды

```bash
make check         # = python -m auditenv.run check --with-tests (без make). ЕДИНСТВЕННАЯ команда проверки (~4 мин): pytest + генерация + валидация + аудит
                   # ложных признаков + политики + парные проверки + кривая сложности +
                   # симуляция жюри + report.html
make test          # только pytest
make report        # пересобрать runs/report.html
make docker-check-hardened  # то же: --read-only, --user 10001, выводы в /tmp
make attacks       # 242 поверхностные атаки через оценщик (~10 с)
make docker-check  # официальный режим: --network none, 2 CPU, 4 ГБ (весь прогон ~12 мин; 1.9.1 прогнан 22.11 на Fedora:
                   # CHECK PASSED; 1.9.3 — тоже, лог artifacts/logs/docker_check.log; усиленный — docker_check_hardened.log)
make docker-isolated  # каждая политика в своём контейнере (~1 мин; 1.9.1: 60/60, 8/8, лог docker_isolated.log)
make hard-audit    # «жёсткий» аудит жюри в полном размере (~3.5 мин): 2000 эп. D, 240 краевых, 96 юникод-пар, 60 с вживую
make replay        # разбор сбоев: проверки жюри на правилах 1.7.0 и 1.8.0 -> artifacts/failure_breakdown.json
```

Перед любым коммитом: `make check` должен закончиться `CHECK PASSED`.

## Правила, которые нельзя нарушать

1. **Среда не читает `private/`.** Только оценщик открывает `truth.json`. Ничего из эталона
   (issue_id, evidence_sets, суммы, seed, подсказки) не должно попасть в наблюдения, `info`,
   тексты ошибок или траектории. Тесты `test_isolation.py` это сканируют.
2. **Никаких сторонних зависимостей в рантайме.** Только стандартная библиотека Python.
   `pytest` и `jsonschema` — только для тестов.
3. **Совместимость с Python 3.11.** Нельзя: обратный слэш внутри `{}` в f-строках,
   синтаксис 3.12+. Проверка: `python3.11 -m compileall -q auditenv tests`.
4. **Детерминизм.** Вся случайность идёт через переданный `rng`, никакого глобального
   `random`, `hash()`, времени или порядка файлов. Генерация должна совпадать побайтно.
5. **Любая новая ошибка вносится как перепроводка** (`unpost_*` → `post_*` с ошибкой),
   чтобы книга сходилась, а в `provenance` осталась причина.
6. **У каждой ошибки — законный двойник** с той же внешней приметой. После изменений
   генератора смотрите таблицу аудита ложных признаков в выводе `make check`.
7. **Доказательства минимальны и достаточны.** Для каждого нового типа добавьте ветку
   в `validate.verify_evidence` и в независимый поиск `find_*`.
8. **Не подгоняйте базовые политики под красивые цифры.** Сложность регулируется данными.
9. Изменение `ENV_VERSION` (`auditenv/__init__.py`) или конфига меняет все эпизоды. Это
   нормально, но после него перегенерируйте всё через `make check` и обновите цифры
   в `DESIGN.md` (раздел 7).
10. **Гранулярность сумм не должна подсказывать ответ.** Новые суммы в генераторе
    создавайте через `with_cents(...)`: копейки должны встречаться и в законных записях,
    и в ошибках. Независимый аудит нашёл именно такой признак (F01).
11. **Ничего не должно ронять `step()`:** ни ввод, ни сбой оценщика (`infra_error`).
12. **Официальный контракт неприкосновенен:** формула награды, −1 за неверную структуру,
    обрыв = пустой ответ, в eval политике ничего не приходит. Всё для удобства обучения —
    только отдельными каналами в режиме train (`experimental_reward`, `feedback`) или
    opt-in (`tool_extensions`). В `feedback` никогда не попадают ID, суммы и доказательства
    эталона — это проверяет тест.
13. Поменяли инструменты, наблюдения, ключи `info` или каналы награды — поднимите
    `API_VERSION`. Поменяли данные — поднимите `ENV_VERSION`. `SEED_SALT` не трогайте:
    тогда данные конфигов, которых правка не касается, останутся прежними. Проверьте
    это сравнением отпечатков (`_fingerprint`) до и после.
15. После любой правки генератора: `make stress` должен дать 0 провалов. Невыполнимый конфиг
    обязан отвергаться в `feasibility_problem` (config.py) с числами, а не падать при генерации.
16. Oracle только для оценщика: его шаги не пишутся в публикуемые траектории (`UNRECORDED_POLICIES`).
17. Состав ошибок по умолчанию откалиброван (DESIGN §6). Минимумы в DEFAULT_CONFIG не ставить:
    они ломают пресет `clean`. Меняете состав — перемерьте сверку на рецепте скрытого набора
    и проверьте, что кривая сложности easy > medium > hard остаётся строгой.
18. Свойства награды измеряются в `auditenv/properties.py`; нарушение роняет `make check`.
19. **Определения проверок жюри (20.11) — контракт.** Правила matcher (точные строки, множества,
    существование доказательств, τ из `policy.json`, выбор среди равных паросочетаний) и
    поведение `judge_adapter.py` проверяются `tests/test_jury_definitions.py` и шагом
    `make check`. Любая правка оценщика или среды должна оставить 92/92.
14. Новый тест, на который ссылаетесь в `docs/REQUIREMENTS.md`, должен существовать: это
    проверяет `test_requirements_matrix_points_to_real_tests`.
20. **`episode_id` в сдаче информационный** (1.8.1, аудит жюри п. 1): не возвращайте его сверку
    в `validate_submission`. Загрузка CSV не должна зависеть от порядка колонок, валидатор — от
    порядка списков в эталоне. После правки генератора или оценщика: `make hard-audit` — 0 провалов.
21. **Проверка не пишет в репозиторий без нужды.** Новые шаги `make check` пишут только в `RUNS`,
    `ARTIFACTS`, `EPISODES` из `auditenv/run.py`; это репозиторий или `$TMPDIR/auditenv-out`.
    Тесты пишут в `tmp_path`. Проверка: копия без права записи под пользователем 10001
    (DESIGN §13).
22. **Новое поле с ID или ссылкой на ID** (в любом файле эпизода, включая ключи объектов) —
    сразу в `auditenv/schemas/id_fields.json`. Иначе `tests/test_id_fields.py` упадёт: после
    переименования в копии останется старый ID.
23. **Правка оценщика** (`grader/matcher.py`, `reward.py`, `episode.py`): потом `make mutation` —
    20/20. Если мутант перестал применяться, обновите его текст в `auditenv/mutation.py`, но не
    удаляйте. Изменили генератор намеренно: `python -m auditenv.run golden --write`, затем
    поднимите `ENV_VERSION`. Поменяли число или утверждение в README — обновите `docs/claims.json`.

## Как добавить тип ошибки

1. Добавить имя в `ERROR_TYPES` (`auditenv/common.py`) и в `schemas/*.schema.json`.
2. Написать инжектор в `errors.py`, зарегистрировать его в `INJECTORS`, добавить
   в `DEFAULT_CONFIG["errors"]`.
3. Добавить `find_<тип>` и ветку `verify_evidence` в `validate.py`.
4. Добавить законного двойника в `company.py` и правило-примету в `shortcuts.py`.
5. Описать определение в `TASK` (`env/core.py`), в `policy.json` (`export.py`) и в `DESIGN.md`.
6. `make check`.

## Что ответили организаторы (19 ноября)

* Политики жюри подключаются через Python-интерфейс `reset/step`. Oracle только у оценщика.
* Скрытые эпизоды генерируются нашим генератором через `reset(seed, config)`; нужно
  документировать, как получить 5 чистых и 5 со взаимодействием (сделано: README,
  встроенные пресеты `auditenv/presets`, `configs/hidden_like.json`). Нужна воспроизводимость содержимого,
  побайтовая идентичность файлов не обязательна.
* Отдельный инструмент перестановки и смены ID не делать без подтверждения.
* Diff удалённых и добавленных проводок с исходными версиями документов достаточен
  для проверки равенств до ошибки (сделано).
* Дополнительные поля в записях допустимы, если они документированы (README, «Словарь данных»).
* ID записи курса: `date:source_currency:target_currency`, уникальность обязательна (проверяется).
* Сеть при сборке образа разрешена, зависимости зафиксированы; при проверке сети нет;
  время политики входит в лимит эпизода (60 с — предварительно).
* **Формат сдачи:** одна папка Google Диска с видео, презентацией и ссылкой на GitHub.
  Ссылка на папку отправляется в личном кабинете с выбором трека. Демо — видео,
  длительность и требования к содержанию пришлют отдельно.
* Ждём от них (по мере готовности): сначала определения проверок, потом назначение
  «четырёх адаптеров», затем требования к видео.
